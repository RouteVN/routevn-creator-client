# Input inventory and validation limits

Status: Phase 1 preparation, September 13, 2026. These are proposed contracts
and measured checked-in examples; no application/model enforcement was added.

The [machine-readable inventory](./input-inventory.json) records action names,
source locations/hashes, emitter coverage, nested holders, conversions, corpus
measurements, and the exact limit values below. The
[action contracts](./action-contracts.md) decide which shapes and contexts are
supported for strict authoring. Presence in an engine schema, legacy fixture,
or conversion helper does not itself make an action supported.

September 18 refresh: this remains the original measured corpus, not a rescan
of current main. The [refresh scenario](./fixtures/scenarios/september-18-contract-refresh.json)
and input inventory's `implementationRefresh` record current schema 15, avatar
preview/default-transform coverage, and the new literal-operation requirement.
Retain historical hashes; refresh the full emitter inventory before enforcement.

## Corpus and reproducibility

The review used current worktree bytes at these repository revisions:

| Repository     | HEAD                                       |
| -------------- | ------------------------------------------ |
| Creator client | `0844141f67bca7e194409095ad6b7a0dd8914053` |
| Creator model  | `4dc3cdaa7805905c98547743b91cf74d3ea8fef2` |
| Route Engine   | `7c8eb55d19b511de5f07dbd95af24fd991d5d892` |

The recorded per-source SHA-256 values identify the inspected bytes even when
a worktree differs from HEAD. The client declares creator-model `1.14.0` and
route-engine-js `1.46.1`; the engine checkout used as reference is `1.46.3`.
The checkout contract must not be assumed to be available in the installed
runtime without verifying the package version used for implementation.

The measurement scope is:

- All tracked `static/templates/*/repository.json`: one shipped template.
- All 3,191 tracked model `tests/compat/**/*.{yaml,yml,json}` artifacts across
  schema archives 1–14, including states, payloads, and command streams.
- All four tracked client `tests/puty/*.spec.yaml` files. These include test
  expectations and therefore are a separate corpus, not additional real
  projects.
- All tracked engine `src/schemas/**/*.yaml` as contract references.
- All 593 tracked client `src/**/*.js` files for action-named mutations and
  shared action-normalizer call sites; all dedicated `commandLine*` emitters,
  generic runtime action definitions, and relevant composition/adapter paths
  received a more specific source review.
- All seven built-in shader filter outputs, generated by invoking the existing
  pure `createCommandLineShaderAdjustmentFilter` helper with each definition's
  maximum parameter value. This captures the generated source strings that
  are absent from the default template.

These are **checked-in examples, not measurements of users' projects**. The
limits deliberately leave substantial room above these small examples. They
are an explicit initial product policy, not evidence that every existing
project fits new-input limits. Historical envelope-1 content is handled
separately below.

JSON/YAML documents were parsed, and compact JSON size was measured as UTF-8
bytes of `JSON.stringify(value)`, without indentation. Multi-document Puty
files were measured as an array of parsed documents. A node is an object,
array, or scalar value; object properties are counted separately. Container
depth starts at 1 for the root container. String/key lengths are UTF-8 bytes,
not JavaScript UTF-16 length. The record includes the file and JSON pointer of
each maximum, plus the largest 20 documents, payloads, and action maps.

For each corpus, the manifest digest is SHA-256 over sorted entries of
`relativePath + NUL + sha256(rawFileBytes) + LF`. This allows a rerun to detect
corpus drift without embedding every legacy fixture again. `sourceFiles`
contains hashes and line counts for the directly referenced files;
`broadSourceScan` covers the full source sweep. AST object-key references and
action-named assignments are audit evidence: UI form configuration also uses
the word `actions` and must not be treated as story actions.

| Runtime pagination        | `incrementSaveLoadPagination`, `decrementSaveLoadPagination`                                                                                                                                                         |

The UI's **Input** mode emits `form`; `input` is not an additional stored
action name. `dedicatedActionEmitters` records each component, submit function
location, and supporting JS/YAML files. The source scan also covers the generic
action editor, Lexical dialogue editing, temporary presentation editing,
section/scene copy operations, and direct whole-map updates. Generic merge or
computed-key code is a reason to validate at the model boundary, not an
unbounded extension mechanism.

The engine reference has 13 presentation and 70 system action names. All 83
appear individually in the JSON inventory, including names with no current
client emitter. The template contains 22 action names; all are represented in
the registered emitter set. The legacy model corpus additionally includes
`say`, including the permissive `say: next` fixture. Preserve that historical
fixture; it does not justify accepting `say` in strict new input.

These command families can introduce action-bearing content:

- `project.set_default_dialogue_avatar_transform`: a non-action main/settings
  command that still requires current-version stamping and strict references.
- `project.create`: the original complete supplied state, including previews,
  controls, and shipped client extensions.
- `line.create` and `line.update_actions`: created maps and effective changed
  action structures, including merge, replacement, and preserved content.
- `layout.create/update` and `control.create/update`: supplied elements,
  keyboard/keyup bindings, and recognized preview data.
- `layout.element.create/update` and `control.element.create/update`:
  effective interactions and newly created elements.
- `layout.schema.upgrade`: an explicit transformation whose resulting action
  content needs the mutation-scope rule defined by the command catalog.

Animation, audio-effect, and transform previews already have closed
resource-specific image/sound/transform slot schemas. They are not additional
action holders and must not be widened to the layout preview contract. The
machine inventory records these non-action preview contracts separately.

Copy, duplicate, paste, and cross-scene operations are current authoring even
when their implementation expands into `scene.create`, `section.create`,
`line.create`, and delete commands. Resource-package imports generate the
ordinary resource commands. The machine inventory records these mappings and
source locations so no additional permissive “import” action schema is needed.

## Nested holders and runtime context

Every nested action map applies the same unknown-name/unknown-field policy
within its explicitly supported context:

| Holder                                                  | Context                                                           |
| ------------------------------------------------------- | ----------------------------------------------------------------- |
| `line.actions`                                          | Line presentation/system contract                                 |
| `choice.items[].events.click.actions`                   | Choice selection                                                  |
| `form.submitActions`, `form.cancelActions`              | Form submission/cancellation                                      |
| `conditional.branches[].actions`                        | Selected conditional branch                                       |
| `showConfirmDialog.confirmActions`, `.cancelActions`    | Confirmation callbacks                                            |
| `random.distribution.outcomes[].actions`                | Engine weighted-random branch; support follows the strict catalog |
| `element.<interaction>.payload.actions`                 | Layout or control element interaction                             |
| `control.keyboard.<key>.payload.actions`                | Keydown                                                           |
| `control.keyup.<key>.payload.actions`                   | Keyup                                                             |
| Recognized preview examples containing any above holder | Owning resource's preview schema                                  |

The model's current element fields include `hover`, `click`, `rightClick`,
`scrollUp`, `scrollDown`, `change`, `submit`, `focusEvent`, `blurEvent`,
`selectionChange`, `compositionStart`, `compositionUpdate`, and
`compositionEnd`. Each needs an explicit context/schema decision, even if its
main picker is not exposed. The strict catalog supplies those decisions.

`_event.value` is emitted for runtime-setting controls, and rendered layout
helpers inject event context and generate confirmation action bindings such
as `${confirmDialog.confirmActions}`. These generated render structures are
distinct from the authored action map. They do not authorize arbitrary
strings, arbitrary `_event` objects, or missing static references in new
Creator input. Contextual slot actions and built-in container bindings must
validate against their actual enclosing layout/control context.

Literal object-variable data is another distinct context. A data key named
`actions` or `confirmActions` remains data where the variable schema permits
bounded JSON. Validators must not recursively reinterpret every object with
such a key as executable content.

## Existing conversions and extension data

The inventory records the exact sources for these current behaviors:

- Dialogue `gui` becomes `ui`; string dialogue content becomes text segments;
  some `clear`/presentation combinations remove `clear` during normalization.
- Background `transformId` removes inline transform fields; unsupported blur
  kernels are rounded to supported values.
- Persistent SFX gets schedule-derived ids. BGM/voice editors normalize legacy
  single-sound data into sound arrays and normalize volume/timing.
- Keyboard aliases are canonicalized; adapters recognize direct `actions`,
  `payload.actions`, and runtime keydown/keyup wrappers.
- Save/load preview code reads `slotId`, `slot`, and `slotKey`; a runtime save
  detector also recognizes `saveSaveSlot`.
- Dialogue variable references, conditional layout overrides, special
  containers, and slider event data are converted for engine/graphics output.
- The form editor carries `formExtras`, replaces submit actions with
  `nextLine`, and currently omits supplied cancellation actions from its
  editable reconstruction.

These findings identify compatibility and emitter tests. They are not a
sanitizer contract: strict validation must inspect the actual new input before
such conversions can erase unsupported fields. Historical decoding does not
run a new cleanup pass.

The current client also owns character spritesheet data and command projection
outside creator-model: `tagIds`, sheet dimensions, frame counts, `jsonData`,
and animation maps are stripped/restored around parts of the model adapter.
The source inventory records the early-return reducer path for
`character.sprite.create/update/delete/move`. Its shipped shape must become
part of the versioned model contract before enforcement. Validating only the
lossy normalized model state would miss the original extension fields.

## Concrete limits for new input

All values below are inclusive maxima. `MiB` means 1,048,576 bytes. These limits
belong to the first strict model contract `M`; tightening recorded validation
rules later requires an explicit supported-version decision. Changing today's
authoring limit must not change the validity of yesterday's recorded command.

| ID                                |          Maximum | Applies to                                                                              |
| --------------------------------- | ---------------: | --------------------------------------------------------------------------------------- |
| `NEW_MODEL_PAYLOAD_BYTES`         |  8,388,544 bytes | Pure model domain payload for one ordinary strict command                               |
| `NEW_MODEL_PROJECT_PAYLOAD_BYTES` | 67,108,800 bytes | Pure model complete `project.create` domain payload                                     |
| `NEW_MODEL_JSON_DEPTH`            |              127 | Domain payload containers, starting at 1; the model does not count an envelope wrapper  |
| `NEW_COMMAND_BYTES`               |            8 MiB | Compact UTF-8 stored wrapper JSON `{mv,commandPayload}` for one ordinary command        |
| `NEW_PROJECT_CREATE_BYTES`        |           64 MiB | Explicit strict full-state `project.create`; replaces the ordinary command byte ceiling |
| `NEW_ENVELOPE_BYTES`              |           16 KiB | Allowed outer command metadata excluding payload; unknown metadata fields are rejected  |
| `NEW_BATCH_BYTES`                 |           64 MiB | Complete compact encoded batch, including command wrappers, metadata, and delimiters    |
| `NEW_BATCH_COMMANDS`              |           16,384 | Submitted logical batch before persistence                                              |
| `NEW_STRING_BYTES`                |            1 MiB | Each string value, unless a narrower domain limit applies                               |
| `NEW_KEY_BYTES`                   |      1,024 bytes | Each own JSON object key; property-path safety rules apply additionally                 |
| `NEW_ARRAY_ITEMS`                 |           65,536 | Each general JSON array                                                                 |
| `NEW_OBJECT_KEYS`                 |           65,536 | Each general object/dictionary                                                          |
| `NEW_JSON_DEPTH`                  |              128 | Nested containers, counting the stored wrapper as depth 1                               |
| `NEW_ACTION_DEPTH`                |               16 | Nested action maps; root map is depth 1, each callback/branch map adds 1                |
| `NEW_EXPRESSION_BYTES`            |     16,384 bytes | Each expression string or compact structured condition/expression                       |
| `NEW_EXPRESSION_DEPTH`            |               32 | Longest parsed/semantic expression AST nesting chain                                    |
| `NEW_EXPRESSION_NODES`            |            4,096 | Nodes in each expression AST                                                            |
| `NEW_CHOICE_ITEMS`                |            1,024 | `choice.items`                                                                          |
| `NEW_FORM_FIELDS`                 |            1,024 | `form.fields` keys                                                                      |
| `NEW_VISUAL_ITEMS`                |            4,096 | Each `visual.items` or `character.items`                                                |
| `NEW_AUDIO_ITEMS`                 |            4,096 | Each sound/item array; aggregate byte/work limits still apply                           |
| `NEW_AUDIO_CHANNELS`              |            4,096 | `sfx.channels`                                                                          |
| `NEW_CONDITIONAL_BRANCHES`        |            1,024 | `conditional.branches`                                                                  |
| `NEW_SHADER_FILTERS`              |                7 | Distinct approved built-in shader filters                                               |
| `NEW_COMMAND_WORK`                |  2,000,000 units | Ordinary strict command validation and its effective affected result                    |
| `NEW_PROJECT_CREATE_WORK`         | 16,000,000 units | Complete newly supplied state validation                                                |
| `NEW_BATCH_WORK`                  | 16,000,000 units | Whole sequential preflight                                                              |

The pure model owns the domain payload, shape, expression, and per-command
work limits. It does not import the envelope-2 codec. Its explicit domain byte
ceilings reserve 64 bytes below the client's 8/64 MiB wrapper ceilings. The
current wrapper adds 27 bytes for `mv:15`, and at most 41 bytes for a positive
safe-integer model version. This leaves space for the version wrapper without
making model validation depend on the spelling of storage keys. The domain
payload depth limit is 127; the client additionally counts its enclosing
wrapper against depth 128. Both checks run on new client input; standalone
model callers receive the same domain limits.

`NEW_BATCH_BYTES`, `NEW_BATCH_COMMANDS`, and `NEW_BATCH_WORK` apply only to one
new-authoring submission request. They are not model replay acceptance limits.
A historical page containing 20,000 independently valid commands, or a full
replay spanning more than 64 MiB, remains valid. Replay applies each recorded
strict command's domain/per-command limits, and uses historical scheduling to
choose manageable chunks. Changing page boundaries must never change whether
an existing history is accepted. An authoring caller cannot label new input a
replay request to bypass the submission boundary.

The action catalog may impose a smaller bound: for example the engine's
weighted-random distribution already caps outcomes at 1,000. The generic
1,024-branch or 65,536-array ceilings do not widen that contract.

The domain byte and cardinality limits are far above this corpus's largest supplied
payloads and arrays. The larger full-state allowance accommodates projects
substantially larger than the 71 KiB default template. The batch count also
respects the existing import format: 2,000 files plus 500 resources in each of
15 supported collections can generate up to 9,500 commands, so a common
1,000-command API limit would break permitted package plans. Existing manifest,
download, and tree limits in [import packages](../import-packages.md) continue
to apply independently. Large file bytes remain outside model command JSON.

JSON depth 128 leaves room for the existing 32-level resource tree policy plus
its surrounding state containers. Action and expression depth limits are
smaller because those trees describe recursive execution, not merely folders.
The string allowance exceeds both the 64-byte longest template string and the
2,005-byte longest generated built-in shader source without making strings
unbounded. These are conservative policy choices; they are not performance
benchmarks or estimates of real users' largest projects.

External API transport must cap uncompressed request bytes before parsing:
one command's appropriate wrapper ceiling plus the 16 KiB envelope allowance,
or the 64 MiB complete batch ceiling. Count both received bytes and the
canonical representation: excessive whitespace or compressed expansion cannot
bypass the transport bound. A domain payload at the strict full-state ceiling can approach the client
wrapper ceiling and need not fit inside a batch after metadata overhead. Use
the single-command entry point or a smaller full-state payload; do not omit
metadata from batch accounting.

For direct JavaScript callers, perform a bounded, side-effect-free structural
scan before cloning or encoding. Reject cycles, accessors/custom serialization,
unsupported prototypes, non-JSON values, and nonfinite numbers; do not invoke
`JSON.stringify` first and accept whatever it silently drops. JSON byte size
can be accumulated while scanning before allocating its full encoded form.

The deterministic work score is the sum of input values/properties, effective
strict-result values/properties, expression AST nodes, and declared indexed
reference checks. Count each logical input/result occurrence once in its
respective pass; a structure used by two commands counts in both commands.
The versioned affected-result scope defines the result being scored. Internal
helper calls, cache hits, or repeated implementation visits must not change
this score. Input and result checks both count, including intermediate batch
results later deleted by another command. Implementations must use bounded
algorithms and indexed reference lookup rather than an uncounted whole-project
scan per reference; scheduling/interruption handles actual runtime work.

Constructing authoritative indexes and running existing compatible checks
over pre-existing content are scheduled infrastructure work. They do not
apply new-input cardinality/byte/work rejection limits to an unrelated legacy
subtree. Actual strict reference lookups and traversal of copied/preserved
content within the affected strict result still count. This keeps ordinary
edits possible in a large old project without allowing an input to request
unbounded new computation.

Do not use a wall-clock deadline to decide schema validity: it would make the
same recorded command pass on one device and fail on another. Interruption is
a cancellation/incomplete-load result, not legacy fallback or a partially
accepted command. Oversized current input fails before any command row is
written. Do not silently split a logical batch, truncate content, or discard
unknown fields to fit a limit.

## Historical reading and scheduling

Envelope-2 history uses its recorded model contract and limits. Envelope-1
history keeps existing compatible validation; new authoring ceilings are not
retroactively applied to it. There is no new total-history byte/count ceiling,
or blanket legacy string/array/depth limit, in this feature.

The following concrete values govern scheduling and working sets, not whether
a legacy story is valid:

| ID                           |        Value | Behavior                                                                       |
| ---------------------------- | -----------: | ------------------------------------------------------------------------------ |
| `HISTORY_PAGE_RECORDS`       |          256 | Target records requested per historical page                                   |
| `HISTORY_PAGE_BYTES`         |        4 MiB | Target decoded page working set; an oversized row is processed alone           |
| `HISTORY_SLICE_MS`           |         8 ms | Cooperative scheduling target between traversal/replay chunks                  |
| `HISTORY_SLICE_WORK`         | 10,000 units | Check cancellation/yield between traversal chunks                              |
| `HISTORY_LARGE_RECORD_BYTES` |       16 MiB | Select an isolated large-record/worker path, without declaring the row invalid |
| `HISTORY_PROGRESS_RECORDS`   |          256 | Publish progress at least each page                                            |

A row is never split into separate commands. An oversized historical
`project.create` receives an explicit large-record loading path, even if it
exceeds today's strict bootstrap limit. JSON and decompression must be safe,
bounded in working memory, and non-executing; use iterative traversal or an
isolated parser when ordinary recursion cannot safely handle the record. The
current generic payload codecs eagerly decode rows, so the implementation
must verify the required adapter/parser support before claiming these memory
and responsiveness properties. These figures do not promise that an existing
synchronous `JSON.parse` can be interrupted every 8 ms.

If a device cannot finish safely, preserve all source bytes and report a
resource/cancellation failure with recovery context. Never skip that event,
change its recorded version, or claim that an interrupted strict replay has
completed. This preserves the distinction between device capacity and schema
incompatibility. These scheduling rules do not replace existing legacy
skip/recovery behavior or introduce a new legacy completeness gate. The
candidate reader must preserve projects that the previous reader can load
on the same supported platform; a new resource regression blocks release.

Historical state-aware replay still needs the authoritative history prefix at
each command's position. Scheduling in smaller pages must not substitute
today's resources for the resources that existed when the command ran, or
change the replay result. The main specification's chronological replay and
checkpoint requirements apply throughout.

## Phase 1 handoff checks

The catalog and fixtures must cover all 41 registered emitted names, the
template's 22 names, every nested holder above, and the character spritesheet
extension before strict writes can be enabled. Engine-only names must have an
explicit support/rejection decision in the catalog. The inventory deliberately
retains the historical `say` example and conversion evidence so compatibility
cannot be inferred from a cleaned replacement fixture.

Before enforcement, verify boundary cases at each exact ceiling, shared
budget accumulation across sequential commands, over-limit intermediate
results, original data versus normalized data, and large historical rows.
These are implementation acceptance tests; writing this document has not
implemented them or measured their runtime performance.
